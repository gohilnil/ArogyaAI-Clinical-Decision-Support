## Abstract

ArogyaAI is an Ayurvedic Clinical Decision Support System that combines machine learning, explainable AI, and generative AI to assist practitioners in disease identification and personalised Ayurvedic treatment recommendation. The system accepts patient symptoms, demographics, and lifestyle information, and classifies likely diseases using a Logistic Regression model trained on 4,201 records across 399 disease classes. The model achieves 88.6% accuracy and 83.7% macro F1 on a held-out test set. Predictions above a 35% confidence threshold are accompanied by a genuine per-feature explanation derived from the model's own logit arithmetic, and a personalised Ayurvedic recommendation generated by Google Gemini. The system is deployed as a React 19 + FastAPI web application with Firebase Authentication, Cloud Firestore for multi-clinic data management, and role-based access control. 83 automated tests cover all major code paths and all pass. The project is academic in nature; results are informational and not a substitute for professional medical advice.

## 1. Introduction

Traditional Ayurvedic medicine has been practised for thousands of years and continues to serve hundreds of millions of patients. Despite this scale, the discipline lacks the structured, data-driven computational tools that modern evidence-based medicine relies on. Practitioners typically depend on experience, traditional texts, and manual observation without access to decision support software that can integrate patient history, symptoms, and constitutional type.

ArogyaAI addresses this gap as an academic research project. It demonstrates the feasibility of applying modern machine learning, large language models, and cloud-native web development to the Ayurvedic clinical domain. The system is designed to assist, not replace, human practitioners.

---

## 2. Problem Statement

Ayurvedic clinical practice faces three specific computational challenges:

1. **Classification complexity:** The range of conditions addressed by Ayurveda is large (399 distinct classes in the training data). No standardised open dataset or ML model exists for this classification task.

2. **Personalised recommendations:** Ayurvedic treatment is constitution-dependent (dosha type). A generic recommendation is less useful than one tailored to the patient's dosha, season, food habits, and medications.

3. **Explainability:** A clinical decision support tool that outputs a label with no explanation cannot be trusted or acted on by a practitioner. Understanding which symptoms and profile features drove a prediction is essential.

## 13. Module Descriptions

### 13.1 Authentication Module
Firebase Auth handles user identity. The frontend sends the Firebase ID token in every prediction request. The backend verifies the token against Google's public RS256 certificates. Firestore rules re-verify role server-side. No service-account private key is held on the server.

### 13.2 Diagnosis Module
The multi-step DiagnosePage collects patient information and symptoms. On submission it calls POST /api/predict, displays the result (disease, confidence, XAI, Gemini recommendation), and allows saving to Firestore.

### 13.3 ML Prediction Service
The prediction_service.py orchestrates: input normalisation → preprocessing → Logistic Regression inference → confidence gate → XAI → Gemini. Each step is isolated in its own module for testability.

### 13.4 XAI Module
explain_prediction() computes per-feature logit contributions from the model's coefficients and the scaled feature vector. The logit identity (intercept + total_contribution == logit) is verified by the test suite.

### 13.5 Generative AI Module
gemini_service.py uses the google-genai SDK with a two-model fallback chain. Prompts include patient profile, predicted disease, and confidence. Provider errors are caught and logged server-side; the client receives a safe fallback message.

### 13.6 Patient Management Module
CRUD operations for patients and assessments in Firestore, enforced by security rules that scope all reads and writes to the doctor's clinic.

### 13.7 Admin Module
Account management, doctor approval/rejection, clinic management, and audit log. Admin has no clinical data access (separation of duties).

## 18. Machine Learning Methodology

### Dataset
- File: enhanced_ayurvedic_treatment_dataset.csv
- Rows: 4,201 | Classes: 399 | Min samples/class: 3 | Median: 6

### Features
- Structured: Age, Height, Weight, BMI, Age_Group, Gender, Dosha, Food_Habits, Medication, Allergies, Season, Weather (12 features)
- TF-IDF: Symptoms text, 807 dimensions
- Total: 819 features

### Preprocessing (training-split-fitted only)
1. LabelEncoder for each categorical column
2. TfidfVectorizer for Symptoms
3. StandardScaler for all 819 features

### Model Selection
3-fold stratified cross-validation on training data:
- Random Forest: mean macro F1 = 0.768
- Logistic Regression: mean macro F1 = 0.836 (WINNER)

Reason for selection: higher F1 AND linear model enables exact XAI.

### Test Metrics (held-out 841 samples)
- Accuracy: 88.6%
- Macro F1: 83.7%
- Macro Precision: 83.1%
- Macro Recall: 86.5%

### Data Leakage Prevention
All preprocessing artifacts (scaler, vectoriser, encoders) were fitted on the training split only. SMOTE evaluated within training data only. Test set used exclusively for evaluation.

## 19. Generative AI Integration

Google Gemini is called via the google-genai SDK after ML inference completes. The prompt includes patient profile, predicted disease, confidence, and a request for Ayurvedic analysis (dosha imbalance, dietary advice, herbal suggestions, lifestyle recommendations). ## 21. Explainable AI

Method: Logit-contribution decomposition for Logistic Regression.

For class k: logit_k = intercept_k + SUM_i(coef[k,i] * x[i])

Each term coef[k,i] * x[i] is the feature's real contribution. Positive = supports the predicted condition. Negative = opposes it. This is not a causal claim; it is the model's own arithmetic.

Properties verified by the test suite:
- explanation.predicted_class == returned prediction
- intercept + total_contribution == model's own logit (to 6 decimal places)
- Features ranked in descending order of |contribution|
- Symptom terms appear only if actually present in the submitted text
- Low-confidence response omits the explanation entirely

Only linear models support this method. explain_prediction() returns None for other estimators.

## 22. Security and Privacy

- Firebase ID tokens verified server-side (RS256) against Google's public certificates. No service-account private key on the server.
- Secrets (GEMINI_API_KEY) are in .env, gitignored, and never committed.
- Firebase API key in frontend is a browser-safe configuration token; it cannot bypass Firestore rules.
- Firestore rules enforce clinic-scoped tenant isolation. No patient can read another patient's data. No doctor can read another clinic's data.
- Admin has account management access but no clinical data access (separation of duties).
- CORS allowlist is explicit; no wildcard is used.
- Rate limiting prevents prediction endpoint abuse.
- 401 error body never leaks stack traces, key material, or quota state.
- Patient data is never sent to the backend ML API; only the submitted form fields are processed.

## 25. Limitations

1. **Dataset size:** 4,201 rows, 399 classes, median 6 samples per class. Many classes are underrepresented. The model's performance is academic; it has not been validated on clinical populations.
2. **Confidence threshold:** The 35% threshold is a heuristic with no clinical calibration. The model's probabilities are not calibrated to true likelihoods.
3. **Gemini output:** Recommendations are AI-generated and not reviewed by a clinical expert.
4. **No OCR:** The system cannot extract symptoms from uploaded documents.
5. **No clinical validation:** The system has no regulatory approval and is not intended for clinical deployment.
6. **Static dataset:** The model does not learn from new cases entered into the system.

## 27. Conclusion

The Logistic Regression model achieves 88.6% accuracy and 83.7% macro F1 on a 399-class classification problem. The XAI implementation provides mathematically verifiable per-feature contributions. The web application implements multi-clinic role-based access control, Firebase authentication, and a comprehensive 83-test automated suite.

The project is academic and the results are informational. ArogyaAI is not a replacement for a qualified practitioner, but it demonstrates a credible path toward data-driven decision support in traditional medicine.

# ArogyaAI — Viva Preparation

## 40+ Questions and Answers for MCA Review 4

---

### Section 1: Project Purpose and Problem Statement

**Q1. What is ArogyaAI and what problem does it solve?**

ArogyaAI is an Ayurvedic Clinical Decision Support System. It addresses the problem that Ayurvedic practitioners lack structured, data-driven tools to assist with disease identification and personalised treatment planning. The system accepts patient symptoms and demographic information, runs machine-learning classification to suggest a likely disease, and provides a personalised Ayurvedic recommendation generated by a large language model. It also gives the practitioner an explainable breakdown of which features drove the prediction.

---

**Q2. Why Ayurvedic medicine specifically?**

Ayurveda is a traditional Indian medical system with a large patient base but limited digital tooling. The system's objectives are academic: to explore whether ML classification on symptom data, combined with generative AI, can provide useful decision support in this domain. We explicitly state that results are informational only and are not a substitute for a qualified practitioner.

---

**Q3. What is the difference between a clinical decision support tool and a diagnostic tool?**

A diagnostic tool claims to definitively identify a disease. A clinical decision support tool provides information to assist a human expert in making their own decision. ArogyaAI is the latter: the model suggests a likely condition and provides evidence for the suggestion (XAI), but a practitioner must evaluate the output. The system's disclaimer states this clearly in every API response.

---

**Q4. What is the difference between disease classification and clinical diagnosis?**

Classification is a machine learning task: a model assigns an input to one of N trained categories based on statistical patterns in training data. Clinical diagnosis is a medical determination made by a qualified professional using history, examination, investigations, and clinical judgement. Our model performs classification; it does not diagnose.

### Section 2: System Architecture

**Q5. Describe the overall system architecture.**

The system has three layers:
1. Frontend: React 19 + TypeScript application, served by Vite. It interacts with Firebase Authentication and Cloud Firestore directly for user and clinical data, and calls the FastAPI backend only for ML prediction.
2. Backend: FastAPI (Python) API with two routes — health check and prediction. The backend loads a Logistic Regression model at startup, runs the full ML pipeline, and calls Google Gemini for the narrative recommendation.
3. Data: Cloud Firestore holds all clinical data (users, patients, assessments) behind role-based security rules. Firebase Auth provides identity.

---

**Q6. Why did you separate the ML backend from the database?**

The ML backend has no need to read or write patient records; it only performs inference on the data sent in a single request. Keeping these concerns separate means the ML service is stateless, easier to test, and can be deployed independently. It also means a bug or downtime in one service does not necessarily affect the other.

---

**Q7. Why use Firebase instead of a traditional database like PostgreSQL?**

Firebase provides managed authentication, a real-time NoSQL database, and built-in server-side security rules — all without operating our own server. For a clinic-scoped multi-tenant application with role-based access, Firestore rules enforce data isolation per clinic without requiring us to write middleware authorization logic in the backend. The trade-off is that Firestore has a document model rather than a relational one, which is appropriate for this use case where each assessment is a self-contained document.

---

**Q8. What is the role of CORS in this project?**

CORS (Cross-Origin Resource Sharing) controls which browser origins are allowed to call the API. Without it, any website could call our prediction endpoint using a user's session. We use an explicit allowlist rather than a wildcard, because a wildcard combined with credentialed requests would allow any origin on the internet to make authenticated calls. The deployed frontend origin is listed explicitly; unrecognised origins receive no allow-origin header and the browser blocks the request.

---

### Section 3: React and Frontend

**Q9. What version of React does ArogyaAI use and what are its key features?**

React 19. Key features used: functional components, hooks (useState, useEffect, useCallback, useMemo), the context provided by the auth hook, React Router DOM v7 for client-side navigation, Framer Motion for animations, and Lucide React for icons.

---

**Q10. What is Vite and why was it chosen?**

Vite is a modern build tool and development server. It uses native ES modules during development (fast startup, no bundling) and Rollup for production builds. It was chosen because it is fast, supports TypeScript and React out of the box, and produces optimised chunked bundles.

---

**Q11. How does the application handle authentication state on the frontend?**

The useAuth hook subscribes to Firebase Auth's onAuthStateChanged listener. When a user signs in, it receives the Firebase user object and opens a Firestore snapshot listener on users/{uid}. The snapshot is held until the write is server-confirmed (hasPendingWrites is false) to prevent a race condition where a newly registered user's profile write is local-only when clinic queries are first issued — causing the server rules to deny access. A 4-second timeout ensures the app does not hang indefinitely if the server is unreachable.

---

**Q12. How are protected routes implemented?**

App.tsx is the router. It checks authLoading, then user, then hasUsableProfile (role present, clinicId present unless admin), then doctor status (pending/rejected → PendingApprovalPage). Each check renders a specific page before the main AppShell is reached. There are no traditional route guards; the state machine at the top of App.tsx gates access.

---

### Section 4: FastAPI Backend

**Q13. What is FastAPI and why was it chosen?**

FastAPI is a modern Python web framework that generates OpenAPI documentation automatically, provides request validation via Pydantic models, supports async handlers, and has excellent performance. It was chosen for its minimal boilerplate, strong typing, and built-in Swagger UI.

---

**Q14. What endpoints does the backend expose?**

Three endpoints:
- GET / — root welcome message with links
- GET /api/health — liveness check: returns status, model type, supported disease count, disclaimer
- POST /api/predict — the main endpoint: requires a valid Firebase ID token, rate-limited, runs ML + Gemini, returns prediction, confidence, recommendation, optional XAI

---

**Q15. How does the backend authenticate requests without a service account key?**

It uses Firebase's public signing certificates. Google publishes RSA public keys at a well-known URL. The backend fetches these (cached in-process for one hour), extracts the key matching the token's kid header, and verifies the RS256 JWT signature. It also checks aud (must match the project ID), iss (must match the Firebase token issuer), and exp/iat. A private key is never held on the server.

---

**Q16. What is Pydantic used for in this project?**

Pydantic models define the request and response schemas for the prediction route. PredictRequest validates incoming data (type, range, and non-empty checks) and provides defaults. PredictResponse defines what the API returns. FastAPI uses these models to generate the Swagger UI and to serialise/deserialise JSON automatically.

---

**Q17. How is rate limiting implemented?**

A per-caller in-memory counter tracks the number of prediction requests within the current minute window. When the count exceeds AROGYA_RATE_LIMIT_PER_MINUTE (default 30), the request is rejected with HTTP 429. The counter key is the caller's uid from their Firebase token, so different users have independent limits.

### Section 5: Machine Learning

**Q18. What ML model does ArogyaAI use?**

Logistic Regression (multinomial, trained with scikit-learn). It was selected over Random Forest by 3-fold cross-validation on the training split: Logistic Regression achieved a mean macro F1 of 0.836 vs Random Forest's 0.768. The model is linear, which means it supports genuine per-feature explanations through its coefficients.

---

**Q19. What is the dataset?**

The dataset is enhanced_ayurvedic_treatment_dataset.csv. It contains 4,201 rows and 399 disease classes. The minimum samples per class is 3 and the median is 6 — a sparse, imbalanced dataset. An 80/20 stratified train/test split was used (3,360 train / 841 test rows). The train split was used to fit all preprocessing artifacts. SMOTE was evaluated within the training data only.

---

**Q20. What are the input features?**

819 features total:
- 12 structured features: Age, Height, Weight, BMI, and 8 label-encoded categoricals (Age Group, Gender, Dosha, Food Habits, Current Medication, Allergies, Season, Weather)
- 807 TF-IDF features from the free-text Symptoms field

---

**Q21. What preprocessing steps are performed?**

1. Map numeric age to an Age_Group string using fixed boundaries
2. Normalise unseen categorical values to the nearest valid encoder class (fallback)
3. Label-encode each categorical column using the fitted encoder
4. TF-IDF vectorise the Symptoms text (807 dimensions)
5. Concatenate structured and TF-IDF features (819 total)
6. StandardScaler transform (fitted on training data only)

---

**Q22. What evaluation metrics does the model achieve?**

On the held-out test set (841 samples):
- Accuracy: 88.6%
- Macro F1: 83.7%
- Macro Precision: 83.1%
- Macro Recall: 86.5%
- Weighted F1: 87.6%

These are honest metrics from an untouched test set; no data leakage occurred because the scaler, vectoriser, and encoders were all fitted on the training split only.

---

**Q23. How do you prevent data leakage?**

Data leakage occurs when information from the test set influences preprocessing (e.g. fitting a scaler on all data before splitting). In this project:
- The train/test split is performed first
- The TF-IDF vectoriser is fitted on training Symptoms only
- The StandardScaler is fitted on training features only
- Label encoders are fitted on training categories only
- SMOTE (if used) is applied only to the training split
- The test set is transformed by (not fitted with) these artifacts and evaluated only after training completes
The artifacts saved in arogyaai_model.joblib were all fitted on the training split.

---

**Q24. How does the confidence threshold work?**

The model's predict_proba returns probabilities across all 399 classes. We take the maximum probability and multiply by 100. If this is below 35%, the API returns "Inconclusive Data" — it declines to name a disease. This is a safety heuristic, not a calibrated cut-off derived from the model's probability distribution. It is documented as such; we do not claim it has clinical validation.

---

**Q25. What is the model's reliability, honestly?**

The model achieves 83.7% macro F1 on the test set with 399 classes and a sparse dataset (median 6 samples per class). This is an academic project result. The model has not been evaluated in a clinical setting, has no regulatory approval, and makes no validated medical claims. Results should be treated as informational suggestions to assist a practitioner, not as diagnoses.

### Section 6: Explainable AI

**Q26. What is XAI and how is it implemented here?**

XAI (Explainable AI) here means genuine per-feature contributions from the deployed model. For Logistic Regression, the model's score (logit) for class k is: logit_k = intercept_k + sum(coef[k,i] * x[i]) where x is the scaled feature vector. Each term coef[k,i]*x[i] is that feature's exact contribution to the score for the predicted condition. These are not approximations; they sum back to the model's logit to within floating-point precision, which the test suite asserts.

---

**Q27. Why can you only provide XAI for a linear model?**

Feature contributions from coefficients (logit decomposition) only work for linear models. A Random Forest would require SHAP values or a different approximation. Because the deployed model is Logistic Regression, we can provide exact contributions from the model's own arithmetic. If a non-linear model were deployed, explain_prediction() returns None rather than fabricating an explanation.

---

**Q28. What is the correct interpretation of a feature contribution?**

A positive contribution means the feature pushed the model's score upward for the predicted condition. A negative contribution pushed it downward. "Supports" and "opposes" are used in the UI. This is NOT a statement that the feature caused the condition; it is a term in the model's scoring arithmetic.

---

### Section 7: Generative AI

**Q29. How is Gemini integrated?**

The backend uses the google-genai SDK (google.generativeai was retired). A Gemini client is built lazily on the first prediction request. A prompt is built from the user's profile, the ML prediction, and the confidence score. The client tries models in a fallback chain (gemini-flash-latest, gemini-flash-lite-latest). If all fail, a safe static message is returned — the ML prediction is unaffected.

---

**Q30. What is prompt engineering in this context?**

The prompt sent to Gemini is structured to produce a clinically-worded Ayurvedic recommendation. It includes: patient demographics, dosha type, predicted disease, confidence level, current medications, allergies, season, and weather. It asks Gemini to identify the primary dosha imbalance and recommend Ayurvedic approaches. The prompt is in backend/ai/prompts.py.

---

**Q31. What happens when Gemini is unavailable?**

The service catches all provider exceptions (including network errors, quota exhaustion, and empty responses), logs the error server-side only, and returns a safe fallback: "AI Ayurvedic explanation is temporarily unavailable. The model prediction shown above is unaffected; please consult a qualified healthcare professional." The fallback message never discloses quota state or credentials.

---

**Q32. Why use provider-maintained model aliases instead of pinned version names?**

Pinned model names (e.g. gemini-2.5-flash, gemini-2.0-flash) were found to return 404 "no longer available to new users" — so a pinned name silently becomes a dead entry in the fallback chain. Provider-maintained -latest aliases (gemini-flash-latest, gemini-flash-lite-latest) always resolve to the current available model, avoiding the failure mode without requiring code changes on every provider retirement.

### Section 8: Database and Authentication

**Q33. What is the Firestore data model?**

Collections:
- users/{uid}: role, clinicId, status, displayName, email
- clinics/{clinicId}: name, address, timestamps
- patients/{patientId}: demographics, clinicId, patientCode
- patients/{patientId}/assessments/{id}: diagnosis session data
- audit_log/{id}: admin action log

---

**Q34. How do Firestore security rules enforce multi-tenancy?**

Each rule function reads the caller's profile document (get(users/uid).data). A doctor's clinicId is compared to the requested patient's clinicId. A doctor may only read patients where resource.data.clinicId == callerProfile.clinicId. A patient may only read their own subtree. An admin manages accounts but has no access to clinical records. The rules are server-evaluated; the client cannot bypass them.

---

**Q35. What happened with Firestore permission errors during development?**

The main class of errors were:
1. Race condition on registration: the profile write was not server-confirmed when the first clinic query fired; the rule read a missing profile and denied. Fixed by holding profile snapshots until hasPendingWrites is false.
2. Missing index: the clinic dashboard used a collection-group query on assessments.clinicId, but the Firestore index only declared COLLECTION_GROUP scope; the patient detail page needed COLLECTION scope for the subcollection query. Fixed by declaring both scopes in firestore.indexes.json.
3. CORS mismatch: the deployed frontend origin was not in the CORS allowlist, so every preflight was rejected. Fixed by adding the exact origin to config.py.

---

**Q36. Why does an admin have no clinicId?**

An admin is a platform operator who manages accounts and onboarding across all clinics. They do not belong to any clinic and have no clinical role. Requiring a clinicId of an admin would assert a tenancy that does not exist and strand the account on the "unprovisioned" screen. The rule functions use .get(k, '') to handle the missing field safely rather than raising an evaluation error.

### Section 9: Testing and Security

**Q37. How many tests does the project have and what do they cover?**

83 automated tests, all passing, in 15.60 seconds. They cover:
- API endpoints (root, health, predict)
- Input validation
- Authentication (missing, malformed, wrong scheme, valid token)
- ML pipeline (preprocessing, inference, confidence gate, fallback)
- Real model integration (no mocks — actual artifact loaded)

---

**Q38. How did you avoid testing mocks in place of real behaviour?**

TestRealPipelineIntegration deliberately does not mock the model. It loads the real artifact and runs the full HTTP → preprocessing → Logistic Regression → XAI path. The logit identity test (intercept + total_contribution == model's own logit) is a mathematical verification that the explanation corresponds to the real model's arithmetic and that preprocessing was not silently changed.

---

**Q39. What security measures are implemented?**

- Firebase ID-token verification (RS256) — no service-account key held on server
- Secrets in .env, never committed (gitignore covers .env, *.key, service account files)
- CORS explicit allowlist (no wildcard)
- Rate limiting per caller
- Firestore server-side rules (multi-tenant isolation)
- No patient data in API responses from the backend (only ML results)
- Gemini API key is backend-only (never exposed to frontend)
- 401 error body never leaks stack traces or key material

### Section 10: Design Decisions and Limitations

**Q40. Why did you choose Logistic Regression over Random Forest?**

3-fold cross-validation on the training split showed Logistic Regression had a mean macro F1 of 0.836 vs Random Forest's 0.768. Additionally, Logistic Regression is a linear model whose coefficients allow genuine per-feature explanations — an important design requirement for the XAI feature. Random Forest would have required SHAP or a similar post-hoc approximation.

---

**Q41. Which parts of the project did you implement yourself?**

All code in the repository under backend/, frontend/src/, ml/, and tests/ was implemented for this project. The model was trained on the dataset in enhanced_ayurvedic_treatment_dataset.csv. External libraries (FastAPI, React, Firebase SDK, scikit-learn, google-genai) are used as dependencies and are not our implementation.

---

**Q42. What are the main limitations of ArogyaAI?**

1. The dataset is small (4,201 rows, 399 classes, median 6 samples/class) — many classes have very few training examples.
2. The confidence threshold (35%) is a heuristic, not a calibrated clinical cut-off.
3. Gemini's recommendations are AI-generated and not clinically validated.
4. The system has no OCR, no lab result integration, no physical examination input.
5. No regulatory approval; not intended for clinical use.

---

**Q43. What would you add as future enhancements?**

1. OCR to extract symptoms from uploaded reports
2. A calibrated confidence threshold derived from the model's probability distribution
3. Longitudinal trend analysis across multiple assessments
4. Multi-language support
5. Integration with lab result systems
6. A mobile application
7. SHAP-based explanations if a non-linear model is deployed

---

**Q44. What happens if Firestore is unavailable during a patient save?**

The Firestore SDK will throw an error, which the frontend catches in a try/catch block in DiagnosePage. The error is displayed to the user. The prediction result already shown on screen is unaffected. The save can be retried.

---

**Q45. How do you ensure the XAI explanation is honest?**

The test suite asserts the logit identity: intercept + total_contribution == model's own computed logit for the predicted class. This is checked to 6 decimal places for the real loaded model. If the explanation computed a different class, used wrong coefficients, or the preprocessing drifted, this test would fail. The test exists precisely to detect silent correctness regressions.
